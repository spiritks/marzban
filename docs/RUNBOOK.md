# Deployment runbook

## 1. Pre-flight

Prepare:

- Panel domain: `panel.example.com`
- Panel HTTPS port: `443` by default, or a custom external port such as `8443`.
- Node domains: `de1.example.com`, `nl1.example.com`, ...
- Admin public IP for SSH and panel access rules.
- Panel public IP for node API firewall rules.

Create DNS A records before starting Caddy/ACME.

## 2. Panel server

```bash
cd /opt/projects/marzban
sudo scripts/install-docker-ubuntu.sh
cp panel/.env.example panel/.env
nano panel/.env
sudo scripts/panel-firewall.sh YOUR_ADMIN_PUBLIC_IP PANEL_HTTPS_PORT
cd panel
sudo docker compose up -d
sudo docker compose logs -f marzban
../scripts/create-admin.sh
```

If OAuth is enabled, browser users should not see Marzban's own login form. The protected `/marzban-login/` bridge uses `SUDO_USERNAME`/`SUDO_PASSWORD` from `panel/.env` to create the Marzban dashboard JWT after the OIDC login succeeds.

Open:

`https://panel.example.com/dashboard/` on port 443, or `https://panel.example.com:PANEL_HTTPS_PORT/dashboard/` when using a custom port.

For a non-standard admin panel port, set `PANEL_HTTPS_PORT` in `panel/.env` and include the same `:PORT` in `PANEL_URL`, `ALLOWED_ORIGINS`, `XRAY_SUBSCRIPTION_URL_PREFIX`, `OAUTH2_PROXY_REDIRECT_URL`, and the OIDC provider callback URI. Keep TCP/80 reachable if Caddy must issue public certificates through ACME HTTP-01.

## 3. Node server

Copy the `node/` directory to each node, for example `/opt/marzban-node`.

```bash
cd /opt/marzban-node
cp .env.example .env
nano .env
sudo /opt/projects/marzban/scripts/install-docker-ubuntu.sh
sudo /opt/projects/marzban/scripts/node-firewall.sh YOUR_ADMIN_PUBLIC_IP PANEL_PUBLIC_IP XRAY_PUBLIC_PORT SERVICE_PORT
sudo docker compose up -d
sudo docker compose logs -f marzban-node
```

Important: Marzban Node requires the client certificate shown in the Marzban panel node dialog:

- save it as `node/data/marzban-node/cert.pem`
- set `SSL_CLIENT_CERT_FILE=/var/lib/marzban-node/cert.pem`

There is no separate key file to copy from the panel for the current `gozargah/marzban-node` container. Do not expose the node control API to the whole internet.

If standard ports are occupied, choose free alternatives and use the same values in the panel UI and on the node. Example for a node where TCP/443 and local 62051 are already occupied:

```dotenv
SERVICE_PORT=62050
XRAY_API_PORT=62052
XRAY_PUBLIC_PORT=8443
```

Then add the node in the panel with API port `62050`, and configure the Xray inbound/user traffic port as `8443` instead of `443`.

## 4. Add nodes in Marzban UI

In the panel:

1. Open Nodes.
2. Add each node with its public domain/IP and control API settings.
3. Confirm node status is Online.
4. If Offline, check firewall, SERVICE_PORT, client certificate path/content, and logs.

## 5. Configure VLESS + REALITY

In Marzban UI/Xray config create inbound(s):

- Protocol: VLESS
- Transport: TCP
- Security: REALITY
- Port: 443, or your configured `XRAY_PUBLIC_PORT` if 443 is occupied on the node
- Flow: `xtls-rprx-vision` when clients support it
- Fingerprint/uTLS: chrome
- SNI/serverName: a reachable TLS 1.3 camouflage site
- Dest: same camouflage site on 443
- Short IDs: generated random hex values, or an empty short ID if a client imports the profile but REALITY handshakes fail
- Reality keypair: generated by Marzban/Xray tooling

Start with one inbound per node on TCP/443 when available. If 443 is already occupied, use a free TCP port such as 8443 and make sure it is opened in the node firewall and set in the Marzban inbound.

If modern clients import the profile but speed/ping tests fail and Xray client logs show `REALITY: received real certificate` or `processed invalid connection`, check the node's bundled xray-core version. Some `gozargah/marzban-node:latest` images can lag behind current clients. Put a newer compatible xray binary at `node/bin/xray` and run the node with:

```bash
docker compose -f docker-compose.yml -f docker-compose.xray-override.yml up -d
```

Then re-save the Marzban core config so the node restarts Xray, and re-import the user subscription.

## 6. Users and provisioning

Create user profiles in Marzban and issue subscription links, not manual per-device configs.

Suggested groups:

- test: 1 day, 2 GB, one node
- basic: 30 days, fixed traffic limit, preferred nodes
- admin: all nodes, high/no limit

Clients:

- Windows: Hiddify Next, v2rayN, Nekoray
- Android: Hiddify Next, v2rayNG
- iOS: Streisand, FoXray, Shadowrocket
- macOS: Hiddify Next, Nekoray, Streisand

## 7. Backups

Run on panel server:

```bash
cd /opt/projects/marzban
scripts/backup-panel.sh
```

Back up off-server:

- `backups/*/db.sqlite3`
- `backups/*/marzban-data.tgz`
- panel `.env`
- node TLS material
- DNS inventory

## 8. Health checks

Useful commands:

```bash
cd /opt/projects/marzban/panel
sudo docker compose ps
sudo docker compose logs --tail=200 marzban
curl -I https://panel.example.com/dashboard/
# or, for a custom panel port:
curl -I https://panel.example.com:PANEL_HTTPS_PORT/dashboard/
```

On node:

```bash
sudo docker compose ps
sudo docker compose logs --tail=200 marzban-node
ss -lntup
```

## 9. Update procedure

1. Run backup.
2. Update panel in maintenance window.
3. Test login and subscription link.
4. Update one non-critical node.
5. Test client connection through that node.
6. Update remaining nodes.

Do not update all nodes at once without a tested rollback path.
